## What It Does

The daemon can listen for SSH next to its HTTP API. Any SSH client then reaches a workspace the way it reaches a machine: `ssh` opens a shell or runs a command, `sftp` and `scp` move files, [Codex](#run-codex-in-a-workspace) runs its tools there, and any [MCP client](#serve-mcp-over-ssh) reaches the workspace's tools. Nothing is installed anywhere and there is no real host behind the door; every command runs in mirage's shell and every file operation goes through the workspace's mounts.

The SSH username names the workspace:

```bash
ssh -p 2222 demo@127.0.0.1                  # interactive shell in workspace "demo"
ssh -p 2222 demo@127.0.0.1 'ls /data | wc -l'   # one command
sftp -P 2222 demo@127.0.0.1                 # file transfer
scp -P 2222 notes.txt demo@127.0.0.1:/data/  # copy in
```

The door is off until a port is set, so a daemon nobody configured for SSH never opens a second port.

## Turn It On

1. Pick a port and add it to `~/.mirage/config.toml`:

   ```toml
   [daemon]
   ssh_port = 2222
   ```

2. Authorize your public key. The file uses OpenSSH's `authorized_keys` format:

   ```bash
   mkdir -p ~/.mirage/ssh
   cat ~/.ssh/id_ed25519.pub >> ~/.mirage/ssh/authorized_keys
   ```

3. Restart the daemon (`mirage daemon restart`) and create a workspace with an id you can type:

   ```bash
   mirage workspace create workspace.yaml --id demo
   ssh -p 2222 demo@127.0.0.1
   ```

The file is read again on every login, so adding or revoking a key takes effect without a restart. On first start the daemon mints an ed25519 host key at `~/.mirage/ssh/host_ed25519_key` and keeps it, so your `known_hosts` entry stays valid across restarts. Both daemons read and write the same OpenSSH key format, so either can serve the other's key.

An `~/.ssh/config` entry saves the flags:

```text
Host mirage-demo
  HostName 127.0.0.1
  Port 2222
  User demo
```

## Settings

Per key the environment variable wins over the `[daemon]` table, which wins over the default. `mirage config list --resolved` shows each one's effective value and where it came from, and `mirage config set ssh_port 2222` writes it.

| Key | Env var | Default | Meaning |
| --- | --- | --- | --- |
| `ssh_port` | `MIRAGE_SSH_PORT` | unset (off) | Port to listen on. |
| `ssh_host` | `MIRAGE_SSH_HOST` | `127.0.0.1` | Interface to bind. Loopback only, like the HTTP API. |
| `ssh_host_key_file` | `MIRAGE_SSH_HOST_KEY_FILE` | `~/.mirage/ssh/host_ed25519_key` | The server's private host key. |
| `ssh_authorized_keys` | `MIRAGE_SSH_AUTHORIZED_KEYS` | `~/.mirage/ssh/authorized_keys` | Public keys allowed to log in. |

The Python daemon needs the `ssh` extra (`pip install 'mirage-ai[ssh]'`); the TypeScript daemon needs `ssh2` installed beside it (`npm install ssh2`). A configured door that cannot open (the port is taken, the library is missing) fails the daemon's start instead of leaving it up without SSH.

## What a Login Gets

- **One session per channel.** Every `ssh` command and every shell runs as a fresh mirage session under its key's profile (see [Bind a key to a profile](#bind-a-key-to-a-profile)), else the workspace's default profile, just as each channel is a fresh process under sshd. A `cd` or `export` never leaks from one channel to another, and two channels never wait on each other's lines. The session is closed when the channel ends.
- **Profiles and policies apply.** SSH lines go through `Workspace.shell`, and SFTP goes through the same mount core the [FUSE mount](/home/setup/fuse) uses, so mount modes, hides, asks and policies answer exactly as they do for a shell in that session. A read-only mount refuses an `sftp put` with "Permission denied".
- **A login environment.** `HOME` is `/`, where every session starts, `USER` and `LOGNAME` are the workspace id, `SSH_CLIENT` and `SSH_CONNECTION` describe the connection, and `TERM` comes from the client's terminal. A variable the profile already set keeps its value, and each one clears the session's `pre_session` gate like any `export`.
- **History.** Typed lines land in `/.bash_history` like any other top-level line. The login environment line does not.
- **An interactive shell.** With a terminal (`ssh` with no command), the door prints `mirage:<cwd>$ `, echoes and edits the line, and treats Ctrl-C as an interrupt: the running line is cancelled and `$?` reads 130, as in bash. Ctrl-D on an empty line or `exit [N]` ends the shell. Without a terminal (`ssh -T host < script`), lines are read from stdin with no prompt, the way `bash -s` reads them.
- **Bounded input.** A non-terminal shell line may contain up to 1 MiB before its newline. Longer lines close the channel with status 1 and `mirage: shell input line too long`; no prefix is executed. Streaming stdin to a command is not subject to the line limit. Terminal editors ring the bell and ignore additional input at their line limit; Backspace and Ctrl-U still work.
- **The client's exit status.** `ssh host cmd` exits with the line's status, and a dropped connection cancels the line it was running.

Only public keys are accepted: no passwords, no keyboard-interactive. Nothing is forwarded: no ports, no agent, no X11. A subsystem other than SFTP, `codex-exec` and `mcp` is refused.

## Bind a key to a profile

A workspace's profiles decide what a session may see and run (see
[Permissions](/home/permissions)). Give a key's line in `authorized_keys` the
`mirage-profile` option and every `ssh`, `sftp` and `scp` channel that key
opens runs under that profile instead of the workspace's default:

```text
mirage-profile="guarded" ssh-ed25519 AAAA... agent-a
ssh-ed25519 AAAA... me
```

The daemon reads the option, never the client, so a key can't choose looser
rules for itself. A sandbox that mounts the workspace over SFTP gets its
agent's view this way: give each sandbox its own key, bound to that agent's
profile. The profile is looked up in the workspace
the login names, so a workspace that defines no profile by that name refuses
the channel (`mirage: cannot open a session: ...`), as does an option that is
bare, empty or given twice. A key without the option keeps the default
profile.

## Run Codex in a Workspace

The [Codex CLI](https://github.com/openai/codex) can keep its agent on your
machine and send every tool call (shell commands, file reads, patches) to a
remote environment. The door answers that protocol itself on the
`codex-exec` subsystem, so Codex's commands run in mirage's shell and its
file calls land on the workspace's mounts. Nothing is installed on the
daemon's side.

Name the environment in `$CODEX_HOME/environments.toml` (`~/.codex` by
default). Codex starts `ssh` itself, so the `~/.ssh/config` entry above
carries the port, user and key:

```toml
default = "mirage"
include_local = false

[[environments]]
id = "mirage"
program = "ssh"
args = ["-T", "mirage-demo", "-s", "codex-exec"]
```

Then start Codex. It checks `-C` on your own disk before it connects, so
pass a directory that exists there and use absolute paths in the
workspace:

```bash
codex -C /
```

What a Codex channel gets:

- **The login's session.** The channel is one session under its key's profile, with the environment an `ssh` login gets. Each command runs as a line in it with the command's own working directory and variables, so a `cd` in one command does not reach the next, as with separate processes. Commands land in `/.bash_history`; file calls do not.
- **The mounts' rules.** File calls go through the same mount core as SFTP, so modes, hides and profiles answer as they do for a shell in that session: a read-only mount refuses a patch.
- **Shell scripts as lines.** Codex runs each command as `bash -lc '<script>'`; the script runs as the line itself. A command Codex pipes no input to reads empty stdin, as from `/dev/null`. An interrupt, or Ctrl-C written to a terminal command, cancels the line with status 130.
- **No file watch.** The protocol has none, so Codex reads again when it needs to, and each read is as fresh as the mount's [cache](/home/cache) and watch make it.

Codex's exec-server protocol is experimental; the door follows Codex
0.147. `http/request`, which routes Codex's network calls through the
environment, is not served.

The ChatGPT app's SSH connections (Settings, Connections, SSH) work
differently: the app starts `codex app-server` on the host and runs the
whole agent there, so it needs a real machine with Codex installed. A Codex
on that machine with the `environments.toml` above sends its tools to the
workspace.

## Serve MCP over SSH

The `mcp` subsystem serves the workspace's [MCP tools](/home/mcp) over MCP's stdio framing. An MCP client that launches a command connects through the `~/.ssh/config` entry above:

```json
{
  "mcpServers": {
    "mirage": { "command": "ssh", "args": ["-T", "mirage-demo", "-s", "mcp"] }
  }
}
```

The channel is one session under its key's profile, so a `cd` in one call holds for the next, and the session closes when the client disconnects.

## Differences Between the Daemons

The two daemons serve the same door, with these differences:

| | Python | TypeScript |
| --- | --- | --- |
| Legacy `scp -O` (the SCP protocol) | Served. | Not served. Modern `scp` uses SFTP and works on both. |
| Terminal line limit | 1024 characters. | 1024 bytes. |
| Command output | Streamed as the line produces it. | Sent when the line finishes, as the HTTP API sends it. |
| Codex command output | Streamed as the command produces it. | Sent when the command finishes. |
| `authorized_keys` options (`from=`, `command=`, ...) | Enforced by asyncssh; `command=` forces the line that runs. | Only `mirage-profile` is read, so a key line carrying any other option is skipped with a warning rather than accepted as if it had none. |
